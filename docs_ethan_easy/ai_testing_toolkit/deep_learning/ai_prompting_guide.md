# AI提示词工程指南

## 🎯 为什么需要学习提示词工程

当你熟练使用了 [start_here](../start_here/) 的基础模板后，可能会遇到这些问题：
- AI生成的测试质量不够高
- 测试场景覆盖不够全面
- 需要针对特殊场景定制提示词
- 想要提高AI理解的准确性

这时候就需要深入学习提示词工程的原理和技巧。

## 🧠 提示词工程基础原理

### 什么是提示词工程

提示词工程（Prompt Engineering）是设计和优化输入给AI的指令，以获得期望输出的技术。

**核心要素**：
- **角色设定**：告诉AI扮演什么角色
- **任务描述**：明确要AI完成什么任务
- **上下文信息**：提供必要的背景信息
- **输出要求**：明确期望的输出格式和内容
- **约束条件**：设定限制和边界条件

### AI理解文本的方式

**AI的特点**：
- 基于概率模型理解文本
- 依赖上下文信息进行推理
- 对明确、结构化的指令响应更好
- 能够模仿训练数据中的模式

**利用这些特点**：
- 提供清晰、具体的指令
- 给出足够的上下文信息
- 使用结构化的格式
- 参考成功的案例模式

## 📝 提示词设计的基本结构

### 标准提示词模板

```
# {任务标题}

## 角色设定
你是一个{专业领域}的{角色类型}，具备{专业能力描述}。

## 任务描述
{明确的任务描述，包括要做什么、为什么做}

## 背景信息
{相关的背景信息，帮助AI理解上下文}

## 输入信息
{具体的输入数据和信息}

## 输出要求
{详细的输出格式和内容要求}

## 约束条件
{限制和边界条件}

## 示例（可选）
{提供示例输入和输出}
```

### 各部分的作用

**角色设定**：
- 激活AI相关的知识领域
- 设定专业水平和视角
- 建立输出的语言风格

**任务描述**：
- 明确AI需要完成的具体任务
- 解释任务的目的和重要性
- 设定任务的范围和边界

**背景信息**：
- 提供必要的上下文
- 帮助AI理解业务场景
- 减少歧义和误解

**输出要求**：
- 明确期望的格式和结构
- 指定内容的详细程度
- 设定质量标准

## 🎯 针对测试场景的提示词技巧

### 技巧1：分层信息组织

**不好的写法**：
```
帮我生成用户管理API的测试用例
```

**好的写法**：
```
# 用户管理API测试用例生成

## 你的角色
你是一个资深的API测试专家，专注于企业级系统的API测试设计。

## 业务背景
- 系统：企业用户管理系统
- 用途：管理企业内部用户账户
- 重要性：核心业务功能，影响所有用户

## API信息
- 接口：/api/users
- 方法：GET, POST, PUT, DELETE
- 认证：JWT Token

## 业务规则
1. 用户名必须唯一
2. 邮箱格式必须正确
3. 只有管理员可以删除用户

## 我需要你生成
详细的测试用例，包括正常场景、异常场景、边界条件
```

### 技巧2：具体化描述

**避免抽象描述**：
- ❌ "测试用户功能"
- ❌ "验证系统性能"
- ❌ "检查数据正确性"

**使用具体描述**：
- ✅ "测试用户注册时邮箱格式验证功能"
- ✅ "验证1000并发用户下的响应时间"
- ✅ "检查订单金额计算的精度和准确性"

### 技巧3：提供示例数据

**不完整的描述**：
```
测试用户输入验证
```

**完整的描述**：
```
测试用户输入验证，包括：
- 有效用户名：john_doe（3-20位字母数字下划线）
- 无效用户名：ab（少于3位）、very_long_username_over_limit（超过20位）
- 有效邮箱：user@company.com
- 无效邮箱：invalid-email、user@
```

### 技巧4：明确输出格式

**模糊的要求**：
```
生成测试用例
```

**明确的要求**：
```
请生成测试用例，每个用例包含：
- 用例编号：TC-001
- 用例名称：清晰的名称
- 测试目标：明确的测试目的
- 前置条件：测试前的准备工作
- 测试步骤：详细的操作步骤
- 测试数据：具体的输入数据
- 预期结果：期望的输出结果
- 优先级：高/中/低

格式：Markdown表格或列表
```

## 🔧 提示词优化技巧

### 优化技巧1：迭代改进

**第一版提示词**：
```
生成登录功能的测试用例
```

**第二版改进**：
```
为Web应用的用户登录功能生成测试用例，包括正常登录和异常情况
```

**第三版优化**：
```
# Web应用登录功能测试用例生成

## 功能描述
用户使用用户名/邮箱和密码登录系统

## 业务规则
- 支持用户名或邮箱登录
- 密码错误3次后锁定
- 记住登录状态7天

## 需要覆盖的场景
1. 正常登录流程
2. 输入验证（空值、格式错误）
3. 认证失败（用户不存在、密码错误）
4. 账户状态（锁定、禁用）
5. 安全功能（记住登录、多次失败）

请生成详细测试用例...
```

### 优化技巧2：关键词强调

使用重要性标记：
- **重要**：用于强调关键信息
- **注意**：用于提醒注意事项
- **必须**：用于强调必要条件

```
## 重要业务规则
**必须验证**：邮箱格式的正确性
**注意**：密码失败次数的累计规则
**重要**：用户权限的严格控制
```

### 优化技巧3：分步骤引导

对于复杂任务，分步骤引导AI：

```
请按以下步骤生成测试方案：

步骤1：分析业务场景，识别核心功能点
步骤2：设计测试场景，覆盖正常和异常情况  
步骤3：编写测试用例，包含详细步骤和数据
步骤4：设计测试数据，包含有效和无效数据
步骤5：提供执行建议，包含工具和环境要求
```

### 优化技巧4：约束条件设定

明确设定边界和限制：

```
## 约束条件
- 测试用例数量：每个功能点5-10个用例
- 复杂度：适合中级测试工程师执行
- 工具限制：使用开源测试工具
- 时间限制：单个用例执行时间<5分钟
- 环境：标准测试环境，无特殊硬件要求
```

## 🚀 高级提示词技巧

### 技巧1：上下文注入

在提示词中注入相关知识：

```
## 测试理论基础
根据等价类划分和边界值分析的测试设计方法，结合以下业务场景...

## 行业最佳实践
参考ISO 29119测试标准和IEEE 829测试文档标准...
```

### 技巧2：多角度验证

要求AI从多个角度验证：

```
请从以下角度验证测试方案的完整性：
1. 功能覆盖角度：是否覆盖所有功能点
2. 用户体验角度：是否考虑用户使用场景
3. 技术实现角度：是否考虑技术限制
4. 业务风险角度：是否覆盖业务风险点
```

### 技巧3：质量控制嵌入

在提示词中嵌入质量检查：

```
生成测试用例后，请自我检查：
- 是否每个用例都有明确的验证点？
- 是否覆盖了正常、异常、边界情况？
- 是否考虑了并发和性能场景？
- 测试数据是否真实可用？
```

### 技巧4：输出后处理

要求AI对输出进行处理：

```
生成测试用例后，请：
1. 按优先级排序（高、中、低）
2. 按执行难度分类（简单、中等、复杂）
3. 识别依赖关系（哪些用例有先后顺序）
4. 估算执行时间（每个用例的大概时间）
```

## 🎯 常见问题和解决方案

### 问题1：AI生成的内容太泛泛而谈

**原因**：提示词缺少具体信息
**解决方案**：
- 提供具体的业务场景
- 给出详细的技术信息
- 明确输出的详细程度
- 提供示例数据

### 问题2：AI理解错了业务需求

**原因**：业务描述不够清晰
**解决方案**：
- 使用准确的业务术语
- 提供业务流程图或示例
- 明确业务规则和约束
- 提供反例说明

### 问题3：生成的测试用例不够实用

**原因**：缺少执行细节
**解决方案**：
- 明确测试执行环境
- 要求提供具体的测试步骤
- 指定测试数据的格式
- 要求考虑实际执行中的问题

### 问题4：测试覆盖不够全面

**原因**：没有系统性的覆盖要求
**解决方案**：
- 提供测试覆盖的checklist
- 要求从多个维度考虑
- 明确必须覆盖的场景
- 要求进行覆盖度检查

## 📊 提示词效果评估

### 评估维度

**准确性**：
- AI是否正确理解了需求？
- 生成的内容是否符合预期？
- 技术信息是否准确？

**完整性**：
- 是否覆盖了所有重要场景？
- 测试用例是否足够详细？
- 是否遗漏了关键信息？

**可用性**：
- 生成的内容是否可以直接使用？
- 是否需要大量修改？
- 执行起来是否现实？

**一致性**：
- 多次使用是否得到一致的结果？
- 格式是否统一？
- 质量是否稳定？

### 改进方法

1. **A/B测试**：对比不同提示词的效果
2. **迭代优化**：根据结果不断改进
3. **团队反馈**：收集团队使用反馈
4. **效果跟踪**：跟踪长期使用效果
