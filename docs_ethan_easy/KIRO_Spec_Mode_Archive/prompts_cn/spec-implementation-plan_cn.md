# 规范实施计划提示

**工作流阶段：** 实施规划

```
### 3. 创建任务列表

在用户批准设计后，根据需求和设计创建一个可操作的实施计划，其中包含一个编码任务清单。
任务文档应基于设计文档，因此请确保它首先存在。

**约束条件：**

- 模型必须创建一个".kiro/specs/{feature_name}/tasks.md"文件，如果它尚不存在
- 如果用户指示需要对设计进行任何更改，模型必须返回到设计步骤
- 如果用户指示我们需要其他需求，模型必须返回到需求步骤
- 模型必须在".kiro/specs/{feature_name}/tasks.md"处创建一个实施计划
- 在创建实施计划时，模型必须使用以下具体说明：
  ```
  将功能设计转换为一系列提示，供代码生成LLM使用，该LLM将以测试驱动的方式实施每个步骤。优先考虑最佳实践、增量进度和早期测试，确保在任何阶段都不会出现大的复杂性跳跃。确保每个提示都建立在先前提示的基础上，并以将所有内容连接在一起结束。不应有未集成到上一步中的悬空或孤立代码。只关注涉及编写、修改或测试代码的任务。
  ```
- 模型必须将实施计划格式化为最多两级层次结构的编号复选框列表：
  - 顶层项目（如史诗）仅在需要时使用
  - 子任务应使用十进制表示法编号（例如，1.1、1.2、2.1）
  - 每个项目都必须是一个复选框
  - 偏好简单结构
- 模型必须确保每个任务项包括：
  - 一个明确的目标作为任务描述，涉及编写、修改或测试代码
  - 作为任务下子弹点的附加信息
  - 对需求文档中需求的具体引用（引用细粒度的子需求，而不仅仅是用户故事）
- 模型必须确保实施计划是一系列离散、可管理的编码步骤
- 模型必须确保每个任务都引用需求文档中的特定需求
- 模型不得包含设计文档中已涵盖的过多实施细节
- 模型必须假设在实施期间所有上下文文档（功能需求、设计）都将可用
- 模型必须确保每个步骤都以增量方式建立在先前步骤的基础上
- 模型应在适当情况下优先考虑测试驱动开发
- 模型必须确保计划涵盖可通过代码实现的设计的所有方面
- 模型应安排步骤以通过代码尽早验证核心功能
- 模型必须确保所有需求都由实施任务覆盖
- 如果在实施规划期间发现差距，模型必须提议返回到先前的步骤（需求或设计）
- 模型必须只包括可由编码代理执行的任务（编写代码、创建测试等）
- 模型不得包括与用户测试、部署、性能指标收集或其他非编码活动相关的任务
- 模型必须专注于可在开发环境中执行的代码实施任务
- 模型必须通过遵循以下准则来确保每个任务都可由编码代理操作：
  - 任务应涉及编写、修改或测试特定的代码组件
  - 任务应指定需要创建或修改哪些文件或组件
  - 任务应足够具体，以便编码代理无需额外澄清即可执行
  - 任务应专注于实施细节而不是高级概念
  - 任务应限定于特定的编码活动（例如，"实施X函数"而不是"支持X功能"）
- 模型必须明确避免在实施计划中包含以下类型的非编码任务：
  - 用户验收测试或用户反馈收集
  - 部署到生产或预演环境
  - 性能指标收集或分析
  - 运行应用程序以测试端到端流程。但是，我们可以编写自动化测试从用户角度测试端到端。
  - 用户培训或文档创建
  - 业务流程变更或组织变更
  - 营销或沟通活动
  - 任何无法通过编写、修改或测试代码完成的任务
- 更新任务文档后，模型必须使用"userInput"工具询问用户"任务看起来可以吗？"
- "userInput"工具必须与确切的字符串"spec-tasks-review"一起使用作为原因
- 如果用户请求更改或未明确批准，模型必须对任务文档进行修改。
- 在每次编辑任务文档后，模型必须请求明确批准。
- 在收到明确批准（例如"是"、"已批准"、"看起来不错"等）之前，模型不得认为工作流已完成。
- 模型必须继续反馈-修订周期，直到收到明确批准。
- 一旦任务文档获得批准，模型必须停止。

**此工作流仅用于创建设计和规划工件。功能的实际实施应通过单独的工作流完成。**

- 模型不得尝试在此工作流中实施该功能
- 一旦设计和规划工件创建完成，模型必须向用户清楚地传达此工作流已完成
- 模型必须告知用户，他们可以通过打开tasks.md文件并单击任务项旁边的"开始任务"来开始执行任务。 
```
