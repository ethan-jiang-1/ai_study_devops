# 需求澄清阶段

## 🎯 为什么要澄清需求？

### 先举个生活中的例子
你要请装修公司装修房子：

**没有澄清需求的情况**：
```
你：我要装修房子
装修公司：好的，我们开始装修
（装修进行中...）
你：等等，我要的是现代简约风格
装修公司：啊？我以为你要欧式风格...
你：还有，我要开放式厨房
装修公司：墙都砌好了，要重新敲掉...
```

**充分澄清需求的情况**：
```
你：我要装修房子
装修公司：请告诉我具体要求...
- 什么风格？现代简约
- 几室几厅？三室两厅
- 预算多少？20万
- 特殊需求？开放式厨房，儿童房要环保
- 入住时间？3个月后
装修公司：明白了，我们设计方案给你看
```

**软件开发也是同样的道理！**

### 需求澄清的定义
需求澄清是指：**通过系统性的方法，将用户的模糊想法转化为清晰、完整、可验证的需求文档，确保所有人对要做的事情理解一致。**

**核心价值**：
- 避免南辕北辙，确保方向正确
- 减少后期返工，控制项目成本
- 提升团队信心，明确项目目标
- 建立验收标准，确保质量交付

## 🔍 需求不清晰的常见问题

### 问题1：需求模糊不清
**症状表现**：
- "我要一个好用的系统"
- "界面要美观大方"
- "性能要快"
- "功能要齐全"

**问题根源**：
- 用户不知道如何表达需求
- 缺乏标准的需求描述方法
- 没有深入了解用户真实需求

**解决方法**：
- 使用结构化的需求模板
- 引导用户描述具体场景
- 通过问答澄清模糊概念

### 问题2：需求理解不一致
**症状表现**：
```
产品经理理解：用户管理系统 = 用户信息管理
研发工程师理解：用户管理系统 = 用户权限管理
测试工程师理解：用户管理系统 = 用户行为管理
```

**问题根源**：
- 没有统一的需求文档
- 口头沟通容易产生歧义
- 缺乏充分的需求讨论

**解决方法**：
- 建立标准的需求文档
- 组织需求评审会议
- 确保所有人理解一致

### 问题3：需求边界不清
**症状表现**：
- 不知道哪些功能包含在项目中
- 不知道哪些功能不包含在项目中
- 项目范围不断扩大（范围蔓延）

**问题根源**：
- 没有明确定义项目边界
- 用户对需求的理解在变化
- 缺乏需求变更控制机制

**解决方法**：
- 明确定义项目范围
- 建立需求变更流程
- 定期确认需求边界

## 📝 EARS格式：需求描述的标准方法

### 什么是EARS格式？
EARS是一种结构化的需求描述格式，包含5个要素：

**E**ntity（实体）：谁
**A**ction（动作）：做什么
**R**esult（结果）：达到什么效果
**S**cenario（场景）：在什么情况下

### EARS格式的基本结构
```
在[场景]下，[实体]需要能够[动作]，以便[结果]。
```

### EARS格式示例

#### 例子1：用户登录
```
❌ 不好的需求描述：
"用户要能登录系统"

✅ 好的需求描述（EARS格式）：
在用户访问系统时，注册用户需要能够通过邮箱和密码登录，以便访问个人账户和系统功能。

详细说明：
- 实体：注册用户
- 场景：用户访问系统时
- 动作：通过邮箱和密码登录
- 结果：访问个人账户和系统功能
```

#### 例子2：数据备份
```
❌ 不好的需求描述：
"系统要能备份数据"

✅ 好的需求描述（EARS格式）：
在每天凌晨2点时，系统需要能够自动备份所有用户数据到云存储，以便在数据丢失时能够恢复。

详细说明：
- 实体：系统
- 场景：每天凌晨2点时
- 动作：自动备份所有用户数据到云存储
- 结果：在数据丢失时能够恢复
```

#### 例子3：权限管理
```
❌ 不好的需求描述：
"管理员要能管理用户权限"

✅ 好的需求描述（EARS格式）：
在用户权限需要调整时，系统管理员需要能够修改用户的角色和权限，以便确保用户只能访问被授权的功能。

详细说明：
- 实体：系统管理员
- 场景：用户权限需要调整时
- 动作：修改用户的角色和权限
- 结果：确保用户只能访问被授权的功能
```

## 📖 用户故事：用户视角的需求描述

### 用户故事的格式
```
作为[用户角色]，我希望[功能描述]，以便[价值说明]。
```

### 用户故事示例

#### 例子1：在线购物
```
作为购物网站的客户，我希望能够将商品添加到购物车，以便批量购买多个商品。

验收标准：
- 用户可以在商品详情页点击"加入购物车"
- 购物车显示已添加商品的数量和总价
- 用户可以修改购物车中商品的数量
- 用户可以删除购物车中的商品
```

#### 例子2：项目管理
```
作为项目经理，我希望能够查看项目进度报告，以便了解项目当前状态和风险。

验收标准：
- 报告显示所有任务的完成状态
- 报告显示项目整体进度百分比
- 报告显示延期的任务和原因
- 报告可以导出为PDF格式
```

#### 例子3：系统管理
```
作为系统管理员，我希望能够监控系统性能，以便及时发现和解决性能问题。

验收标准：
- 实时显示CPU、内存、磁盘使用率
- 当资源使用率超过80%时发出警告
- 记录性能数据历史，支持30天查询
- 支持设置自定义监控指标
```

## ✅ 需求澄清的检查清单

### 需求完整性检查

#### 功能需求检查
- [ ] **核心功能**：系统的主要功能都描述清楚了吗？
- [ ] **辅助功能**：系统的辅助功能都考虑了吗？
- [ ] **异常处理**：各种异常情况的处理方式都定义了吗？
- [ ] **边界条件**：极端情况下的系统行为都考虑了吗？

#### 非功能需求检查
- [ ] **性能要求**：响应时间、并发用户数等都明确了吗？
- [ ] **可用性要求**：系统可用性、故障恢复时间等都定义了吗？
- [ ] **安全要求**：数据安全、访问控制等都考虑了吗？
- [ ] **兼容性要求**：浏览器、操作系统等兼容性都确认了吗？

### 需求清晰性检查

#### 描述清晰度
- [ ] **术语统一**：专业术语都有明确定义吗？
- [ ] **无歧义**：需求描述有没有可能产生不同理解？
- [ ] **具体量化**：性能指标、数量限制等都量化了吗？
- [ ] **可验证**：每个需求都有明确的验收标准吗？

#### 理解一致性
- [ ] **团队理解**：所有团队成员对需求理解一致吗？
- [ ] **用户确认**：用户对需求描述确认无误吗？
- [ ] **文档化**：需求都写成文档了吗？
- [ ] **版本控制**：需求变更都有记录吗？

## 🎭 不同角色在需求澄清中的职责

### 产品经理 👩‍💼
**主要职责**：需求收集和整理
**具体工作**：
- 与用户沟通，收集原始需求
- 使用EARS格式规范化需求描述
- 编写用户故事和验收标准
- 组织需求评审会议

**工作技巧**：
- 多问"为什么"，了解需求背后的真实动机
- 使用原型或草图帮助用户表达需求
- 记录需求变更的原因和影响
- 保持需求文档的更新和维护

### 研发工程师 👨‍💻
**主要职责**：技术可行性评估
**具体工作**：
- 评估需求的技术可行性
- 识别技术风险和难点
- 估算开发工作量
- 提出技术约束和建议

**工作技巧**：
- 从技术角度分析需求的合理性
- 提出技术替代方案
- 识别需求中的技术陷阱
- 与产品经理协商技术方案

### 测试工程师 🧪
**主要职责**：需求可测试性评估
**具体工作**：
- 评估需求的可测试性
- 识别测试难点和风险
- 提出测试约束和建议
- 参与验收标准的制定

**工作技巧**：
- 从测试角度分析需求完整性
- 识别需求中的测试盲点
- 提出可测试性改进建议
- 与产品经理协商验收标准

### 项目经理 👨‍💼
**主要职责**：需求管理和控制
**具体工作**：
- 组织需求评审会议
- 管理需求变更流程
- 控制需求范围蔓延
- 跟踪需求实现进度

**工作技巧**：
- 建立需求变更控制机制
- 平衡各方需求和约束
- 确保需求文档的质量
- 监控需求实现的进度

## 💡 需求澄清的最佳实践

### 实践1：分层次澄清需求
```
第1层：业务需求
- 为什么要做这个项目？
- 要解决什么业务问题？
- 预期达到什么效果？

第2层：用户需求
- 谁会使用这个系统？
- 用户要完成什么任务？
- 用户的使用场景是什么？

第3层：功能需求
- 系统要提供什么功能？
- 功能的具体行为是什么？
- 功能的边界和约束是什么？

第4层：非功能需求
- 性能要求是什么？
- 安全要求是什么？
- 兼容性要求是什么？
```

### 实践2：迭代式需求澄清
```
第1轮：收集粗略需求
- 了解基本情况
- 识别主要功能
- 确定项目边界

第2轮：详细需求分析
- 深入了解业务流程
- 详细描述功能需求
- 识别非功能需求

第3轮：需求确认和优化
- 确认需求理解正确
- 优化需求描述
- 制定验收标准

第4轮：需求最终确认
- 所有相关方确认需求
- 建立需求基线
- 制定变更控制流程
```

### 实践3：多视角需求分析
```
业务视角：
- 这个需求对业务有什么价值？
- 不实现这个需求会有什么影响？
- 有没有其他方式实现同样的价值？

用户视角：
- 用户真的需要这个功能吗？
- 用户会怎样使用这个功能？
- 这个功能对用户体验有什么影响？

技术视角：
- 这个需求技术上可行吗？
- 实现这个需求有什么技术风险？
- 有没有更好的技术方案？

测试视角：
- 这个需求怎样验证？
- 有哪些测试场景？
- 测试的难点在哪里？
```

## 🎯 需求澄清的成功标准

### 定量标准
- **需求完整性**：90%以上的功能都有明确描述
- **需求清晰度**：95%以上的需求无歧义
- **需求一致性**：100%的团队成员理解一致
- **需求可测性**：100%的需求都有验收标准

### 定性标准
- **用户满意**：用户对需求描述满意
- **团队认可**：团队成员认可需求合理
- **技术可行**：技术方案可以实现需求
- **测试可行**：测试方案可以验证需求

### 检验方法
- **需求评审**：组织正式的需求评审会议
- **原型验证**：制作原型让用户验证需求
- **技术评估**：技术团队评估需求可行性
- **测试评估**：测试团队评估需求可测性

---

**记住**：需求澄清是整个项目成功的基础。花时间把需求搞清楚，后面的工作就会事半功倍。模糊的需求是项目失败的最大根源。

**下一步**：需求澄清完成后，进入 [设计文档阶段](./stage2_design.md)，学习如何设计技术方案来实现这些需求。
