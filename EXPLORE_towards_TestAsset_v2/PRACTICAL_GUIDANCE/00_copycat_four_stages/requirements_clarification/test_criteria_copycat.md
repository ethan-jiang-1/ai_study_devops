# 验收标准制定 - 模板指南

## 🎯 模板目的

将业务需求转化为具体的、可测试的验收标准，为后续的测试计划制定奠定基础。

**核心作用**：
- 明确"怎样算成功"的具体标准
- 为测试人员提供明确的测试目标
- 为开发人员提供清晰的完成标准
- 为产品经理提供验收依据

**时间预期**：2-3分钟完成标准制定

## 📏 验收标准制定原则

### SMART原则
- **S**pecific（具体的）：标准要明确具体，不能模糊
- **M**easurable（可测量的）：能够量化或明确判断
- **A**chievable（可达到的）：在当前条件下可以实现
- **R**elevant（相关的）：与功能需求直接相关
- **T**ime-bound（有时限的）：有明确的时间或条件限制

### 三层验收标准
1. **功能正确性**：功能是否按预期工作
2. **性能合规性**：性能是否满足要求
3. **用户可接受性**：用户体验是否达标

## 📋 验收标准模板

### 基础模板结构

```markdown
## [功能点名称] 验收标准

### 功能性标准
**正常情况验收**：
- [ ] [具体的正常情况标准，如"输入正确用户名密码能成功登录"]
- [ ] [结果验证标准，如"登录成功后跳转到用户首页"]
- [ ] [状态变更标准，如"用户登录状态在系统中正确记录"]

**异常情况验收**：
- [ ] [异常输入处理，如"错误密码显示'密码错误'提示"]
- [ ] [边界条件处理，如"空用户名显示'请输入用户名'提示"]
- [ ] [系统保护标准，如"连续5次失败后账户暂时锁定"]

**边界值验收**：
- [ ] [最小值情况，如"用户名最短3位字符能正常处理"]
- [ ] [最大值情况，如"用户名最长20位字符能正常处理"]
- [ ] [临界值情况，如"密码长度恰好8位能正常验证"]

### 性能标准
- [ ] **响应时间**：[如"登录验证响应时间 < 2秒"]
- [ ] **并发处理**：[如"支持100个用户同时登录而不影响性能"]
- [ ] **资源使用**：[如"内存使用增长 < 10MB per session"]

### 安全标准
- [ ] **数据保护**：[如"密码在传输和存储时都进行加密"]
- [ ] **访问控制**：[如"未登录用户无法访问受保护页面"]
- [ ] **会话管理**：[如"会话在30分钟无活动后自动过期"]

### 用户体验标准
- [ ] **界面友好性**：[如"错误提示信息清晰易懂"]
- [ ] **操作便利性**：[如"支持Tab键在输入框间切换"]
- [ ] **反馈及时性**：[如"操作后立即显示处理状态"]
```

## 🎪 实用填写示例

### 示例：用户登录功能验收标准

```markdown
## 用户登录功能 验收标准

### 功能性标准
**正常情况验收**：
- [ ] 输入正确的用户名和密码组合，点击登录按钮能成功登录
- [ ] 登录成功后自动跳转到用户个人首页
- [ ] 登录状态在浏览器会话期间保持有效
- [ ] 登录成功后显示用户欢迎信息

**异常情况验收**：
- [ ] 输入错误密码显示"用户名或密码错误"提示
- [ ] 输入不存在的用户名显示"用户名或密码错误"提示
- [ ] 空用户名或密码提交显示"请输入用户名和密码"提示
- [ ] 连续3次登录失败后显示验证码输入框
- [ ] 连续5次登录失败后账户锁定5分钟

**边界值验收**：
- [ ] 用户名长度3-20位字符都能正常处理
- [ ] 密码长度8-128位字符都能正常验证
- [ ] 用户名包含字母、数字、下划线能正确识别

### 性能标准
- [ ] **响应时间**：登录验证响应时间 < 2秒（99%情况下）
- [ ] **并发处理**：支持100个用户同时登录不出现错误
- [ ] **可用性**：登录功能可用性 > 99.9%

### 安全标准
- [ ] **密码保护**：密码在网络传输时使用HTTPS加密
- [ ] **会话安全**：会话ID使用安全随机算法生成
- [ ] **暴力破解防护**：IP连续失败10次后临时封禁1小时

### 用户体验标准
- [ ] **界面响应**：点击登录按钮后立即显示"登录中..."状态
- [ ] **错误提示**：错误信息清晰明确，不暴露系统内部信息
- [ ] **便利操作**：支持Enter键提交登录表单
```

## 🔧 验收标准制定技巧

### 技巧1：从用户角度思考
```
不要写：系统验证用户凭据并返回认证令牌
应该写：用户输入正确用户名密码后能成功进入系统
```

### 技巧2：使用可验证的动词
```
✅ 好的动词：显示、跳转、记录、计算、发送、接收
❌ 模糊动词：处理、管理、优化、提升、保证
```

### 技巧3：包含具体的判断标准
```
不要写：系统性能良好
应该写：页面加载时间 < 3秒，支持1000个并发用户
```

### 技巧4：考虑完整的用户场景
```
不只是：用户能够登录
还要包括：登录后能正常使用系统功能，登出时正确清理状态
```

## ✅ 质量检查清单

### 完整性检查
- [ ] 每个功能需求都有对应的验收标准
- [ ] 涵盖了正常、异常、边界三种情况
- [ ] 包含了功能、性能、安全、体验四个维度
- [ ] 考虑了不同用户类型的使用场景

### 可测试性检查
- [ ] 每个标准都是可以具体测试的
- [ ] 验证方法明确，测试人员知道如何操作
- [ ] 成功/失败的判断标准清晰
- [ ] 避免了主观性的评判标准

### 合理性检查
- [ ] 标准要求在技术和资源限制下可以达成
- [ ] 性能指标符合行业标准和用户期望
- [ ] 安全要求与系统风险等级匹配
- [ ] 用户体验要求与目标用户群体匹配

### 协作友好性检查
- [ ] 使用业务语言，各角色都能理解
- [ ] 产品经理认可验收标准的业务合理性
- [ ] 开发人员理解实现要求和完成标准
- [ ] 测试人员能够基于标准设计测试用例

## 📊 验收标准的分级

### A级标准（必须满足）
关键功能的核心验收标准，不满足则功能不可用
- 核心业务流程的正确性
- 基本性能要求
- 关键安全要求

### B级标准（应该满足）
重要但非关键的验收标准，影响用户体验但不影响基本使用
- 异常情况的友好处理
- 性能优化要求
- 用户体验改进

### C级标准（可以满足）
锦上添花的验收标准，资源充足时实现
- 高级用户体验特性
- 性能优化目标
- 扩展功能特性

## 🎯 与测试计划的连接

### 验收标准如何服务测试计划
1. **测试用例设计基础**：每个验收标准对应至少一个测试用例
2. **测试范围确定**：明确哪些功能点需要测试
3. **测试优先级指导**：A/B/C级标准对应不同测试优先级
4. **测试完成标准**：所有A级标准通过，B级标准通过率>90%

### 输出到下一阶段
- **明确的测试目标**：为设计阶段提供测试策略制定依据
- **量化的质量标准**：为实施阶段提供开发完成标准
- **验证方法指导**：为执行阶段提供具体的验证步骤

- 什么性能水平是可以接受的？
- 用户体验达到什么程度算合格？
