## 🔥 TL;DR - 立即开始深度思考
> **目标**：从机械填空转向理解为什么 - 深度理解需求分析的设计原理
> 
> **方式**：通过5个核心问题引导思考，每个问题2分钟深入探索

> **行动**：选择你的项目 → 逐个回答思考问题 → 完成深度需求分析

## 🤔 核心思考引导（5个关键问题）

### 1️⃣ 为什么软件开发是"贯通流程"而非独立技能？⏰ 3分钟思考
```
深度思考（贯通流程理解）：
- 想想你经历过的项目，前一个阶段的输出如何影响后一个阶段？
- 如果需求理解错误，设计、规划、执行全部白费，为什么？
- 为什么说"需求澄清的输出必须能直接驱动设计阶段"？

关键认知转变：
从：需求澄清 → 设计文档 → 实施规划 → 任务执行（独立技能）
到：需求输出→设计输入→规划输入→执行输入（严格依赖）

我对贯通流程的理解：
[思考并写下你的理解]
```

### 2️⃣ 什么样的需求描述才算"清晰"？⏰ 3分钟思考
```
对比思考：

✅ 清晰需求："用户点击登录后，2秒内显示个人主页"

深度思考：
- 你能从这个对比中发现什么规律？
- "清晰"的标准到底是什么？
- 如何判断一个需求描述是否足够清晰？

我的清晰需求标准：
[基于思考写下你的判断标准]
```

### 3️⃣ 如何发现隐藏的需求？⏰ 3分钟思考
```
场景思考：
用户说："我要一个登录功能"
表面需求：用户名密码验证
隐藏需求：？？？

深度挖掘思考：
- 用户忘记密码怎么办？
- 多次登录失败怎么处理？
- 用户信息安全如何保障？
- 不同角色的权限如何区分？

发现隐藏需求的方法：
[总结你发现的挖掘方法]
```

### 4️⃣ 需求阶段的核心职责：验收标准可测试性 ⏰ 3分钟思考
```
关键职责认知（专业分工原则）：
需求阶段专注：用户故事梳理 + 验收标准定义
不涉及：代码探索、具体测试实施

深度思考：
- 为什么需求阶段不需要考虑具体的测试实现？
- "验收标准可测试性"与"测试实施"有什么区别？ 
- 需求阶段如何为后续的TDD阶段做好准备？

重要区分：
✅ 需求阶段：定义"如何验收"（验收标准可测试性）
❌ 需求阶段：设计"如何测试"（测试实施是后续阶段的事）

我对验收标准可测试性的理解：
[写下你对这个职责分工的理解]
```

### 5️⃣ 为什么实施规划阶段是"TDD的真正主场"？⏰ 2分钟思考
```
阶段职责思考：
四个阶段的TDD职责分工：
- 需求澄清：验收标准的可测试性（不过度强调测试）
- 设计文档：可测试性设计，为TDD做准备（但不实施TDD）
- 实施规划：⭐ TDD的真正主场 - "优先考虑测试驱动开发"
- 任务执行：严格TDD实施，红绿重构循环

深度思考：
- 为什么TDD不是全程贯穿的概念？
- 实施规划阶段做什么样的"TDD转换"工作？
- 这样的职责分工对项目成功有什么价值？

我对TDD正确定位的理解：
[写下你对TDD阶段分工的理解]
```

## 🚀 AI深度协作技巧

### 🤖 从简单提问到多轮对话
**照猫画虎阶段**：AI，这里应该填什么？
**理解应用阶段**：与AI进行2-3轮深度探讨

**基于贯通流程的多轮协作示例**：
```
第1轮：AI，帮我分析[项目名]的核心需求，重点关注用户故事梳理
第2轮：这些需求如何转化为清晰的验收标准？重点是可测试性而非测试实施
第3轮：我的需求输出能否直接成为设计阶段的输入？有哪些地方需要完善？
```

### 🔍 AI协作最佳实践
- **具体化提问**：不说"帮我分析需求"，而说"帮我分析登录功能的安全性需求"
- **追问深度**：AI给出答案后，继续问"为什么"、"如何验证"、"还有其他可能吗"
- **场景化验证**：让AI帮你模拟不同场景下的需求表现

## 🚨 避免这些思维陷阱

### 1️⃣ 急于求解陷阱
❌ **错误思维**：快速填完空格就算完成  
✅ **正确思维**：每个问题都值得深入思考2-3分钟  

### 2️⃣ 标准答案陷阱
❌ **错误思维**：寻找"标准答案"来填写  
✅ **正确思维**：基于自己的思考形成独特见解  

### 3️⃣ 理论脱离实践陷阱
❌ **错误思维**：只在脑中思考，不结合具体项目  
✅ **正确思维**：每个思考都要在具体项目中验证
