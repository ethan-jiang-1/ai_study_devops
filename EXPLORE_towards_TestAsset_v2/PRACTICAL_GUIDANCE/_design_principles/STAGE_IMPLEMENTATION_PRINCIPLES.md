## ⭐ TDD转换职责原则

### 🎯 核心职责定义
**实施规划是TDD转换的真正主场**：将功能设计转换为测试驱动的编码任务

### 📋 TDD转换具体要求
```
核心转换任务：
"将功能设计转换为一系列提示，供代码生成LLM使用，该LLM将以测试驱动的方式实施每个步骤。
优先考虑最佳实践、增量进度和早期测试，确保在任何阶段都不会出现大的复杂性跳跃。"
```

### 🧪 测试驱动思维要求
- **测试优先设计**：每个任务都要考虑如何测试
- **红绿重构循环**：任务序列要支持TDD循环
- **早期测试验证**：安排步骤以通过代码尽早验证核心功能
- **可测试任务分解**：确保每个任务都能被独立测试

### ✅ 转换质量标准
- [ ] 每个任务都包含测试驱动的执行方式
- [ ] 任务序列支持增量验证
- [ ] 复杂功能被分解为可测试的小步骤
- [ ] 测试用例能直接指导代码生成

**创作要求**：实施规划必须体现TDD主场定位，所有任务都要服务于测试驱动开发

## 📋 任务格式标准原则

### 🔒 强制格式要求
```markdown
# 实施任务清单

## 任务列表

### 1. [功能模块名称]
- [ ] 1.1 [具体编码任务] 
  - 任务目标：[明确的编码目标]
  - 需求引用：参考requirements.md第X条
  - 测试要求：[具体的测试验证方法]
  - 预期输出：[该任务的交付物]

- [ ] 1.2 [具体编码任务]
  - 任务目标：[明确的编码目标]
  - 需求引用：参考requirements.md第X条
  - 测试要求：[具体的测试验证方法] 
  - 预期输出：[该任务的交付物]

### 2. [功能模块名称]
[重复相同格式]
```

### 📊 格式约束细则
- **最多两级层次结构**：顶层项目（如史诗）仅在需要时使用
- **十进制编号**：子任务使用十进制表示法（1.1、1.2、2.1）
- **复选框强制**：每个项目都必须是一个复选框
- **偏好简单结构**：避免过度复杂的嵌套

### 🎯 任务描述要求
- **明确目标**：任务描述必须是具体的编码目标
- **代码导向**：涉及编写、修改或测试特定的代码组件
- **可操作性**：编码代理无需额外澄清即可执行
- **需求追溯**：每个任务都引用需求文档中的具体需求

**创作要求**：严格遵循格式标准，确保任务列表的一致性和可操作性

## 🔄 增量构建原则

### 📈 增量进度要求
- **步骤依赖**：每个步骤都以增量方式建立在先前步骤的基础上
- **连接性**：确保每个提示都建立在先前提示的基础上
- **无悬空代码**：不应有未集成到上一步中的悬空或孤立代码
- **集成收尾**：以将所有内容连接在一起结束

### 🧩 复杂性控制
- **避免大跳跃**：确保在任何阶段都不会出现大的复杂性跳跃
- **渐进式实现**：复杂功能分解为多个简单步骤
- **验证节点**：关键节点设置验证和测试

### 🔗 任务连贯性
```
正确的任务序列示例：
1.1 创建基础数据模型 → 为1.2提供数据结构基础
1.2 实现基础CRUD操作 → 基于1.1的数据模型
1.3 添加业务逻辑验证 → 基于1.2的基础操作
1.4 集成测试验证 → 验证1.1-1.3的集成效果
```

**创作要求**：确保任务序列的逻辑连贯性，每个任务都有明确的前置依赖

## 🔒 代码导向约束原则

### ✅ 必须包含的任务类型
- **编写代码**：实现特定功能的代码组件
- **修改代码**：基于需求变更修改现有代码
- **测试代码**：编写单元测试、集成测试等
- **调试代码**：修复bug和性能问题

### ❌ 严禁包含的任务类型
- **用户验收测试**：需要用户参与的测试活动
- **部署到生产**：部署和运维相关任务
- **性能指标收集**：监控和数据收集任务
- **用户培训**：培训和文档编写任务
- **业务流程变更**：组织和流程变更任务
- **营销沟通活动**：市场推广相关任务

### 🎯 可操作性检查标准
- [ ] 任务涉及编写、修改或测试特定的代码组件
- [ ] 任务指定需要创建或修改哪些文件或组件
- [ ] 任务足够具体，编码代理无需额外澄清即可执行
- [ ] 任务专注于实施细节而不是高级概念
- [ ] 任务限定于特定的编码活动

**创作要求**：严格筛选任务类型，确保所有任务都是编码代理可执行的

## 🔒 质量门禁原则

### 📋 审批流程要求
```
实施计划完成后的强制流程：
1. 创建tasks.md文件，包含完整的任务列表
2. 验证所有任务都可由编码代理执行
3. 确保任务覆盖设计的所有方面
4. 必须询问："任务看起来可以吗？"
5. 等待明确批准（"是"、"已批准"、"看起来不错"等）
6. 如未获批准，必须修改任务文档
7. 继续反馈-修订循环，直到获得明确批准
```

### 🎯 规划质量检查
- [ ] 实施计划是一系列离散、可管理的编码步骤
- [ ] 每个任务都引用需求文档中的特定需求
- [ ] 计划涵盖可通过代码实现的设计的所有方面
- [ ] 所有需求都由实施任务覆盖
- [ ] 任务序列支持TDD实施方式

### 🔄 差距处理机制
- **需求差距**：如发现需求理解差距，必须提议返回需求步骤
- **设计差距**：如发现设计不完整，必须提议返回设计步骤
- **实施差距**：在规划期间发现的技术难点必须解决

**创作要求**：实施规划的质量门禁确保任务计划的完整性和可执行性

## ⚡ 输入输出对接要求

### 📥 输入来源
- **架构方案**：来自设计阶段的技术架构
- **接口测试设计**：组件接口和测试策略
- **设计决策**：重要的技术选择和约束

### 📤 输出目标
- **详细实施计划**：完整的tasks.md文件
- **完备测试计划**：每个任务的测试验证方法
- **执行指导**：为任务执行阶段提供明确指导

### 🔗 对接机制
**输出必须能直接驱动任务执行阶段**：
- 任务列表能指导AI精确执行
- 测试要求能支持TDD循环
- 执行顺序能确保增量构建

**创作要求**：确保实施规划输出能无缝成为任务执行输入，任务计划具备可执行性

## 🚨 常见违反原则的行为

### ❌ TDD转换违反
- 任务中不包含测试驱动的执行方式
- 忽略测试优先的设计思维
- 任务序列不支持红绿重构循环

### ❌ 格式标准违反
- 任务描述过于抽象或高层
- 缺少需求文档的具体引用
- 任务层次结构过于复杂

### ❌ 代码导向违反
- 包含部署、培训等非编码任务
- 任务描述不够具体，难以执行
- 忽略任务的可操作性要求

### ❌ 增量构建违反
- 任务之间缺少逻辑依赖关系
- 复杂性跳跃过大
- 出现悬空的孤立任务

**修正策略**：发现违反后重新审视任务分解，确保符合TDD转换和增量构建要求

## 🎯 应用此原则

### 📝 内容创作者使用方法
1. **规划前准备**：深入理解设计文档，明确TDD转换目标
2. **规划中执行**：严格按照格式标准分解任务，确保增量构建
3. **规划后验证**：使用质量检查清单全面检查
4. **交付时把关**：严格执行质量门禁流程

### 🔧 TDD转换技巧
- **测试先行思维**：为每个功能先考虑如何测试
- **小步快跑**：将复杂功能分解为多个可测试的小任务
- **验证节点**：在关键节点设置集成测试和验证

### 📊 质量保证要求
- 定期review任务列表是否符合TDD转换要求
- 验证任务的可操作性和连贯性
- 确保测试计划的完备性
