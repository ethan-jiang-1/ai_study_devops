# 设计文档阶段工程化约束原则

## 🔥 TL;DR - 立即开始
> **目标**：内容创作者掌握设计文档阶段的严格工程化约束标准
> 
> **行动**：1. 确保[输入依赖](#📥-输入依赖原则) → 2. 执行[研究要求](#🔍-研究要求原则) → 3. 应用[结构标准](#🏗️-结构标准原则)

---

## 📥 输入依赖原则

### 🔒 严格输入要求
- **必须基于需求文档**：设计文档必须严格基于已批准的requirements.md
- **需求优先存在**：确保需求文档首先存在且获得批准
- **完整性检查**：验证需求文档包含所有必要的用户故事和验收标准

### ❌ 禁止行为
- **无需求设计**：绝不允许在没有需求文档的情况下开始设计
- **假设需求**：不能基于假设或口头描述进行设计
- **跳过验证**：不能跳过需求文档的完整性检查

### ✅ 正确做法
- **需求追溯**：设计中的每个决策都能追溯到具体需求
- **覆盖验证**：确保设计满足所有已确定的功能需求
- **版本同步**：基于最新批准版本的需求文档

**创作要求**：任何设计阶段内容都必须明确标注其需求来源，确保输入依赖的透明性

## 🔍 研究要求原则

### 📋 强制研究流程
```
设计前必须完成的研究步骤：
1. 根据功能需求确定需要研究的技术领域
2. 进行必要的技术调研和方案对比
3. 在对话线程中建立研究上下文
4. 总结将为设计提供信息的关键发现
5. 引用来源并包含相关链接
```

### 🎯 研究领域识别
- **技术栈选择**：基于需求特点确定合适的技术栈
- **架构模式**：研究适用的架构模式和设计模式
- **性能要求**：调研性能基准和优化策略
- **安全考虑**：研究相关的安全最佳实践
- **第三方集成**：调研需要集成的外部服务和API

### 📊 研究质量标准
- **来源可信**：使用权威技术文档、官方指南、知名技术博客
- **信息时效**：确保研究信息是最新的、相关的
- **对比分析**：提供多种方案的优劣对比
- **决策依据**：明确说明选择特定技术方案的理由

**创作要求**：研究过程必须透明，关键发现必须记录，为设计决策提供充分依据

## 🏗️ 结构标准原则

### 📋 固定文档结构
```markdown
# 功能设计文档

## 1. 概述
[基于需求的功能概述，说明设计目标和范围]

## 2. 架构
[整体架构设计，包含组件关系和数据流]

## 3. 组件和接口
[各组件的详细设计和接口定义]

## 4. 数据模型
[数据结构设计和存储策略]

## 5. 错误处理
[异常情况处理策略和错误恢复机制]

## 6. 测试策略
[针对设计的测试方法和验证策略]

## 7. 设计决策记录
[重要设计决策及其理由说明]
```

### 🎯 各部分详细要求

#### 📊 架构部分要求
- **组件图**：使用Mermaid绘制架构图（如适用）
- **数据流**：清晰描述数据在系统中的流转路径
- **边界定义**：明确系统边界和外部依赖

#### 🔗 接口部分要求
- **接口规范**：详细定义输入输出格式
- **通信协议**：说明组件间的通信方式
- **版本策略**：考虑接口的版本管理

#### 🗄️ 数据模型要求
- **实体关系**：定义核心实体及其关系
- **约束规则**：说明数据完整性约束
- **存储策略**：选择合适的存储方案

**创作要求**：严格按照固定结构组织内容，确保设计文档的完整性和一致性

## 🔒 质量门禁原则

### 📋 审批流程要求
```
设计文档完成后的强制流程：
1. 创建design.md文件，包含所有必需部分
2. 将研究结果直接纳入设计过程
3. 必须询问："设计看起来可以吗？如果可以，我们可以继续制定实施计划。"
4. 等待明确批准（"是"、"已批准"、"看起来不错"等）
5. 如未获批准，必须修改设计文档
6. 继续反馈-修订循环，直到获得明确批准
```

### 🎯 设计质量检查
- [ ] 设计满足需求澄清过程中确定的所有功能需求
- [ ] 研究结果已充分应用到设计决策中
- [ ] 设计决策及其理由已明确记录
- [ ] 包含适当的图表或视觉表示
- [ ] 考虑了可测试性设计要求
- [ ] 错误处理和边缘情况已覆盖

### 🔄 反馈处理机制
- **差距识别**：如发现需求理解差距，必须提议返回需求澄清
- **用户反馈整合**：必须将所有用户反馈纳入设计文档
- **技术决策征询**：可就具体技术决策征求用户意见

**创作要求**：设计阶段的质量门禁确保技术方案的可行性和完整性

## ⚡ 输入输出对接要求

### 📥 输入来源
- **需求规格**：来自需求阶段的requirements.md
- **验收测试框架**：EARS格式的验收标准
- **业务约束**：边缘情况和技术约束条件

### 📤 输出目标
- **技术架构方案**：完整的系统设计文档
- **接口测试设计**：基于组件接口的测试策略
- **实施指导**：为实施规划提供技术基础

### 🔗 对接机制
**输出必须能直接驱动实施规划阶段**：
- 架构方案能指导任务分解
- 接口设计能指导测试用例设计
- 技术决策能影响实施优先级

**创作要求**：确保设计阶段输出能无缝成为实施规划阶段输入，技术方案具备可实施性

---

## 🎯 可测试性设计要求

### 🧪 测试策略规划
- **单元测试**：为每个组件设计单元测试策略
- **集成测试**：规划组件间接口的集成测试
- **端到端测试**：设计用户场景的完整测试流程

### 📊 验证点设计
- **功能验证**：每个功能模块的验证方法
- **性能验证**：关键性能指标的测试方法
- **安全验证**：安全特性的验证策略

### 🔄 TDD准备
- **测试优先思维**：为TDD实施做好设计准备
- **测试接口**：设计便于测试的组件接口
- **模拟策略**：规划测试中的依赖模拟方案

**创作要求**：设计阶段为TDD主场（实施规划）做好充分准备，但不实施具体TDD

## 🚨 常见违反原则的行为

### ❌ 输入依赖违反
- 在没有需求文档的情况下开始设计
- 基于口头描述而非正式需求文档
- 忽略需求中的关键约束条件

### ❌ 研究要求违反
- 跳过技术调研直接选择方案
- 使用过时或不可信的技术信息
- 未记录设计决策的依据

### ❌ 结构标准违反
- 缺少必需的文档部分
- 架构图不清晰或缺失
- 未考虑错误处理和测试策略

**修正策略**：发现违反后立即补充缺失部分，重新执行正确的设计流程

## 🎯 应用此原则

### 📝 内容创作者使用方法
1. **设计前准备**：确保需求文档完整，制定研究计划
2. **设计中执行**：严格按照结构标准组织内容，记录设计决策
3. **设计后验证**：使用质量检查清单全面检查
4. **交付时把关**：严格执行质量门禁流程

### 🔧 质量保证要求
- 定期review设计文档是否符合结构标准
- 验证研究质量和设计决策的合理性
- 确保可测试性设计要求得到满足
