## ⏰ 执行节奏控制原则

### 🎯 一次一个任务的严格要求
**核心约束**：一次只专注于一个任务，不要为其他任务实现功能

### 📋 执行节奏具体规范
```
严格的执行流程：
1. 从任务列表中选择当前要执行的任务
2. 如果任务有子任务，必须从子任务开始
3. 专注执行当前任务，不涉及其他任务的功能
4. 完成当前任务后，立即停下来让用户查看
5. 绝不自动继续列表中的下一个任务
6. 等待用户确认或指定下一个任务
```

### 🔒 停止检查机制
- **任务完成标志**：当前任务的所有要求都已满足
- **强制停止**：完成后必须停下来，不能继续
- **用户确认**：等待用户查看和确认结果
- **下一步指示**：等待用户明确指定下一个任务

### 🚨 禁止行为
- **任务跳跃**：不能跳过当前任务去做其他任务
- **功能越界**：不能为其他任务实现功能
- **自动推进**：不能在用户未要求的情况下自动继续下一任务
- **批量执行**：不能一次性执行多个任务

**创作要求**：任务执行必须严格遵循节奏控制，确保每个任务的质量和用户的控制权

## 📚 上下文完整性原则

### 📋 执行前强制检查
**在执行任何任务之前，必须确保已阅读以下文档**：
- **requirements.md**：功能需求文档
- **design.md**：设计文档  
- **tasks.md**：任务分解文档

### ❌ 无上下文执行的危险
```
没有需求或设计就执行任务 → 导致不准确的实现
缺少任务详细信息 → 导致实现偏离预期
忽略验收标准 → 导致质量不符合要求
```

### ✅ 上下文完整性检查清单
- [ ] 已完整阅读requirements.md，理解功能需求
- [ ] 已完整阅读design.md，理解技术架构
- [ ] 已完整阅读tasks.md，理解任务分解
- [ ] 理解当前任务在整体项目中的位置
- [ ] 明确当前任务的输入和输出要求

### 🔗 上下文应用要求
- **需求对照**：实现过程中持续对照需求文档
- **设计遵循**：严格按照设计文档的架构实现
- **任务细节**：严格按照任务描述的具体要求
- **版本一致**：确保使用最新版本的上下文文档

**创作要求**：绝不允许在上下文不完整的情况下执行任务，确保实现的准确性

## ✅ 验证机制原则

### 🎯 基于需求的验证要求
**根据任务或其详细信息中指定的任何需求验证实现**

### 📋 验证层次结构
```
多层次验证机制：
1. 任务级验证：当前任务的具体要求是否满足
2. 需求级验证：相关的需求条目是否得到正确实现
3. 设计级验证：实现是否符合设计文档的架构
4. 集成级验证：与已有功能的集成是否正常
```

### 🧪 验证方法要求
- **功能验证**：验证功能是否按预期工作
- **边界验证**：验证边缘情况的处理
- **性能验证**：验证是否满足性能要求
- **安全验证**：验证安全相关的实现

### 📊 验证标准检查
- [ ] 实现满足任务描述的所有要求
- [ ] 实现符合引用的需求条目
- [ ] 实现遵循设计文档的约束
- [ ] 实现通过了相应的测试用例
- [ ] 实现处理了已知的边缘情况

**创作要求**：每个任务完成后必须进行全面验证，确保实现质量

## 🔍 任务问题处理原则

### 🎯 区分执行请求和信息查询
**重要区别**：用户可能询问有关任务的问题，而不想执行它们

### 📋 问题类型识别
```
信息查询类（不执行任务）：
- "下一个任务是什么？"
- "这个功能有哪些任务？"
- "任务X的详细要求是什么？"

执行请求类（需要执行任务）：
- "执行任务1.1"
- "开始实现用户登录功能"
- "继续下一个任务"
```

### 💡 正确响应策略
- **信息查询**：只提供信息，不启动任何任务执行
- **执行请求**：按照执行节奏控制原则执行任务
- **模糊请求**：主动询问用户的具体意图

### 🚨 错误处理
- **任务未指定**：查看任务列表并就下一个要执行的任务提出建议
- **任务不存在**：提醒用户任务不存在，提供可选任务列表
- **依赖未满足**：提醒用户完成前置任务

**创作要求**：准确识别用户意图，避免不必要的任务执行和遗漏真正的执行请求

## ⚡ 输入输出对接要求

### 📥 输入来源
- **实施计划**：来自实施规划阶段的tasks.md
- **完备测试计划**：每个任务的测试验证方法
- **执行上下文**：requirements.md、design.md的完整内容

### 📤 输出目标
- **通过测试的代码**：符合所有验证要求的可执行代码
- **执行日志**：详细的执行过程和结果记录
- **质量报告**：验证结果和质量评估

### 🔗 TDD循环对接
**支持严格的TDD实施**：
- **红阶段**：先写测试，确保测试失败
- **绿阶段**：实现最小代码让测试通过
- **重构阶段**：在保持测试通过的前提下优化代码

**创作要求**：确保任务执行严格按照TDD循环，每个任务都有完整的测试验证

## 🎯 AI精确执行支撑

### 🤖 AI执行特点适配
- **指令明确**：任务描述必须足够明确，AI无需猜测
- **上下文完整**：提供AI执行所需的全部上下文信息
- **验证自动化**：设计可自动化的验证机制
- **错误处理**：预设常见错误的处理方式

### 📋 AI协作最佳实践
- **分步指导**：将复杂任务分解为AI可理解的小步骤
- **示例提供**：提供代码示例和模式参考
- **标准检查**：使用标准化的质量检查方式
- **反馈循环**：建立AI执行结果的反馈机制

### 🔄 持续改进机制
- **执行记录**：记录AI执行的成功和失败模式
- **模式总结**：总结有效的AI协作模式
- **标准优化**：基于实践结果优化执行标准

**创作要求**：任务执行阶段要充分考虑AI的特点，设计AI友好的执行流程

## 🚨 常见违反原则的行为

### ❌ 执行节奏违反
- 一次性执行多个任务而不停止
- 完成任务后自动继续下一个任务
- 为其他任务实现功能

### ❌ 上下文完整性违反
- 没有阅读需求文档就开始实现
- 忽略设计文档的架构约束
- 不理解任务在整体项目中的位置

### ❌ 验证机制违反
- 不根据需求验证实现
- 跳过测试用例的验证
- 忽略边缘情况的处理

### ❌ 问题处理违反
- 对信息查询也启动任务执行
- 对执行请求只提供信息不执行
- 不明确用户意图就贸然行动

**修正策略**：发现违反后立即停止，重新按照正确流程执行，确保质量和节奏

## 🎯 应用此原则

### 📝 内容创作者使用方法
1. **执行前准备**：确保上下文文档完整，理解任务要求
2. **执行中控制**：严格遵循一次一个任务的节奏
3. **执行后验证**：全面验证实现质量和需求符合性
4. **交付时确认**：等待用户确认再进行下一步

### 🤖 AI执行优化技巧
- **任务拆解**：将复杂任务进一步拆解为AI可处理的小任务
- **上下文提供**：为AI提供充分的执行上下文
- **验证自动化**：设计自动化的验证脚本和检查机制

### 📊 质量保证要求
- 定期review执行流程是否符合节奏控制要求
- 验证上下文完整性和验证机制的有效性
- 持续优化AI执行的支撑机制
